  • Ein Prozess (npm start oder docker-compose.single.yml): Redis optional — Live-Events bleiben im Speicher des einen Node-Prozesses.
  • Compose-Standard (docker-compose.yml): zwei App-Container (pulse, pulse-b) teilen ./data und REDIS_URL. nginx verteilt Anfragen; WebSockets bleiben pro Client an einer Instanz (ip_hash).
  • Health: GET /api/health (Version, Speicher, Event-Loop) und GET /api/health/ready (Readiness für Deploy/Rollback).

Datenfluss: Join und Live-Update

  1. Teilnehmende öffnen #/join/<code> — der Browser lädt die Session per REST (GET /api/sessions/<code>).
  2. Parallel baut die App eine WebSocket-Verbindung zu wss://…/ws auf und sendet join mit Rolle participant.
  3. Der Server antwortet mit session (Folien, aktive Folie, Event-Metadaten). Bei geplanten Events: Seite sichtbar, Stimmen erst nach Status aktiv (Wartehinweis statt Fehlerbanner).
  4. Stimmen, Wörter und Q&A laufen über WebSocket (vote, word, …); der Server persistiert in SQLite und broadcastet gebündelt (Standard 100 ms) an alle Clients der Session.
  5. Bei mehreren App-Instanzen publiziert der bearbeitende Prozess über Redis; die andere Instanz leitet an ihre WebSocket-Clients weiter.

Last- und Stabilitätstests

Vor Releases und nach Deploy können Admins/Entwickler reproduzierbare Lasttests fahren:

npm run load-test
node scripts/load-test.js --participants=300 --allow-remote --url=https://<domain>
node scripts/load-test.js --participants=500 --batch-size=500 --allow-remote --url=https://<domain>
node scripts/load-test.js --participants=500 --duration-minutes=2 --allow-remote --url=https://<domain>

Messgrößen: Join-Latenz (WebSocket), Vote-Latenz, Fehlerquote, Health während des Laufs. Release-Gates: Join-P95 ≤ 800 ms, Vote-P95 ≤ 500 ms, Fehlerquote ≤ 1 %. Produktions-Lasttests nur mit --allow-remote und eigener Test-Session — nicht gegen Live-Publikums-Events.
